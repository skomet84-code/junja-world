# JUNJA VILLAGE v37 — 실험 경제 스냅샷·장부 검증·복구 설계

작성: 2026-10-19 KST

## 구현 내용
- v36 서버 권위 **시험용 골드/농장** 계정을 유지하며, 거래 성공 때마다 v37 복구용 전체 상태 스냅샷을 저장합니다.
- 저장 대상: 서버 시험 골드, 농작물과 가공품 재고, 농장 칸, 주민 주문 상태, 명성. **본게임 XP/레벨/기존 재산은 포함하지 않음.**
- 새 테이블: `village_economy_v37_checkpoints` (기존 `village_saves`, `village_wallets` 변경 없음).
- 첫 거래에서 이전 시험 경제 상태를 기준 스냅샷으로 만든 뒤, 각 성공 거래에 새 스냅샷을 추가합니다.
- 스냅샷은 고정렬 JSON에 SHA-256을 적용하고 **이전 기록 해시·거래 UUID·버전**을 포함해 연결합니다.
- DB 트랜잭션: 유저별 행 잠금 → 원장 검사 → 서버 규칙 실행 → 계정·거래 영수증·스냅샷 같이 갱신 → COMMIT.
- 마지막 스냅샷과 현재 계정 잔액/재고가 다르면 **409와 함께 거래 중지**합니다. 잘못된 버전으로 자동 덮어쓰지 않습니다.
- GET은 본인 계정 최근 25개 체인 검증 결과를 제공하며, 다른 계정의 재화 정보는 반환하지 않습니다.
- 기능 플래그 `ENABLE_VILLAGE_ECONOMY_V37=true`가 없으면 API는 503으로 잠겨 있습니다.

## 검증 범위
### 실제 PostgreSQL 17 자동 테스트
`.github/workflows/village-economy-v37-postgres.yml`
- 외부 운영 DB와 무관한 매 실행 일회성 Postgres 17 컨테이너로 실행됩니다.
- 동일 거래 UUID 5건을 동시 전송하고 **한 건만 실제 차감/기록**하는지 검사.
- 서버 재배 시간, 재료/가격 조작 차단, 트랜잭션 취소, 영수증 누적, SHA 체인 검증.
- **오로지 일회성 테스트 DB 안에서만** 계정 상태를 고의로 변조해 거래 중단을 검증한 후, 검증된 체크포인트로 복구해 재검증합니다.
- CI 테스트 파일은 환경변수 `JUNJA_V37_DISPOSABLE_DB=true`와 localhost:5432 전용 테스트 DSN이 없으면 실행을 거절합니다.

### Neon 분리 스테이징
- 프로젝트: `junja-village-auth-prod` (현재 운영 원본)
- 원본 브랜치: `main`; 스테이징 브랜치: `village-v37-ledger-staging-20261019`.
- 스테이징 브랜치 ID: `br-super-hat-a1tnv11i`.
- v36 실험 지갑·영수증 + v37 복구 스냅샷 **테이블을 분리 브랜치에만** 설치하고 존재를 읽기 전용 쿼리로 확인했습니다.
- 실제 API → 스테이징 Neon 인증 → 거래까지의 E2E 연결 테스트는 **아직 수행하지 않았습니다**. 실제 유저 데이터에 손대지 않았습니다.
- 스테이징 컴퓨트는 테스트 후 비용 방지를 위해 수동 정지(suspend)를 요청했습니다. 다음 테스트 전 상태를 확인하세요.
- 별도 브랜치도 저장 공간/컴퓨트 비용이 발생할 수 있어 장기 유지 여부는 소유자가 판단해야 합니다.

## 출시 전 반드시 충족할 조건
1. Neon 원본/스테이징 백업 확인, 새 SQL `migrations/037_checkpoint_chain.sql` 검토.
2. 본게임 레벨 초기화/저장 오류를 재현하고 원인·복구 경로 별도 해결. 이 v37 스냅샷은 **기존 게임 레벨을 복구하지 않습니다**.
3. 스테이징 Vercel에 **별도 DB 연결 문자열** 설정, 테스트 플래그 ON, 운영 플래그 OFF.
4. 계정별 가입/재접속, 2인 동시 거래, 네트워크 단절 후 동일 UUID 재요청, 모바일 Safari 실제 기기 확인.
5. 기록 이상 감지 시 작업을 중지하고 **담당자가 백업 + 거래 원장 + 체크포인트 일치 여부를 검토**한 뒤 수동 복구; 자동 롤백 금지.
6. 서버 관리 기능이 본게임 지갑으로 **무검증 골드 전환**하는 기능을 만들지 않습니다.
7. 운영 DB 변경/병합/공식 배포는 별도 검증 후 결정.

## 현재 단계의 한계
- 거래 행마다 상태 전체를 저장하여 테이블이 증가합니다. 사용자 수가 많아지면 정책에 따라 **백업/파티셔닝/아카이브**가 필요합니다. 무단으로 기록 삭제하지 않습니다.
- SHA-256 무결성은 예상치 못한 덮어쓰기를 찾는 기능입니다. 데이터베이스 관리자가 임의 변경할 수 있다면 **서명 기반 위조 방지 보증은 아닙니다**.
- 캐릭터 레벨·거래소·다른 사용자 간 교환·서버 신뢰형 자산 전체 이행은 후속 단계입니다.
- Vercel 기존 연결 권한 문제(403)는 아직 별도 해결이 필요합니다.

## 롤백/비상 대응
- 거래 이상 시 즉시 v37 기능 플래그 OFF → API 503, 기존 운영 캐릭터 데이터 그대로 유지.
- 스테이징 데이터는 별도 브랜치에 있으므로 운영 마이그레이션이 아닙니다.
- 스키마·스냅샷·테스트 브랜치 삭제는 승인 없이 진행하지 않습니다.
