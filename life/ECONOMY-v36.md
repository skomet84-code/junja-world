# 준자마을 v36 · 서버 관리 생활 경제 시험장
2026-10-18

## 개발 의도
v34/v35 개인 농장 생활 시스템은 브라우저가 재고/골드를 계산하므로 그대로 유저 간 거래소에 연결하면 안 됩니다.
v36은 **별도 서버 계정 경제**를 구현해 이를 검증합니다. 운영 중인 v32 플레이어의 레벨/골드/아이템은 건드리지 않습니다.

## 범위
- 기존 준자마을 로그인 쿠키로 세션 인증, POST 같은 출처 JSON 검사
- DB: `village_economy_v36_accounts`, `village_economy_v36_events` (신규 표 전용)
- 서버 생성 시험 계정: 1,500 시험 G, 6칸 농장. 기존 `village_wallets` G와 **합쳐지거나 교환되지 않음**
- 심기/성장 시간/수확/판매/가공/주민 납품/농장 확장
- 서버가 결정하는 가격, 수량, 시간 및 누적 명성
- 트랜잭션 내 행 잠금/원자 업데이트/이벤트 영수증 저장
- 중복 요청 ID: 동일 내용이면 동일 영수증 반환, 내용이 달라지면 409 거부
- 클라이언트의 현재 시간/가격/보상/XP/잔액 입력은 거래에 사용하지 않음

## 안전장치
- `ENABLE_VILLAGE_ECONOMY_V36=true` 환경변수가 없으면 API 503, UI에서 준비 중 안내
- 임의 SQL 실행, 자동 스키마 변경 또는 라이브 계정 데이터 가져오기 없음
- 스키마는 `migrations/036_secure_economy.sql`로 **수동** 검토 후 적용
- 실서비스 계정의 `village_saves`, `village_wallets`는 변경하지 않음
- 하나의 SQL 트랜잭션으로 지갑/농장/이벤트를 묶어 부분 성공 방지

## 기능 검증
```
cd life
npm install
npm test
npm run build
```
`test_secure_economy_v36.mjs`는 결정론적 규칙을 확인합니다.
`test_secure_economy_api_v36.mjs`는 모의 PostgreSQL 인터페이스로 로그인/CSRF/중복 영수증/거래 원자성을 확인합니다.
CI가 모두 통과해야만 다음 단계로 이동합니다.

## 단계별 릴리스 (운영 DB 보호 필수)
1. 실제 서버 DB **사전 백업**, 스테이징 DB 별도 준비
2. 스테이징 DB에서 스키마 리뷰/SQL 실행
3. 스테이징에서 세션 인증, 트랜잭션 경합, 반복 클릭 및 재접속 확인
4. 다중 브라우저·iOS Safari·중복 요청/부하 테스트
5. 유저에게 독립 시험 재화임을 고지한 상태에서 기능 플래그로 내부 테스트
6. 검증 전까지 운영 골드/아이템으로 환전, 이전, 판매/거래소 개방 금지

## 남은 과제
- 현재 테스트는 모의 SQL 백엔드를 사용했으며 실 DB 경쟁조건/장애 복구까지 검증한 것은 아닙니다.
- 거래 완료 후 느린 네트워크나 다중 탭에서도 캐시가 최신인지 서버 재조회 정책 필요
- 시즌 랭킹, 플레이어 간 거래, 시세·재화 발행량 지표, 거래 제재/어뷰징 대응은 미구현
- 기존 v34/v35 콘텐츠를 운영 서버의 계정 권위 재고로 전환할 안전한 이행 과정 필요
- 실제 Vercel 배포는 연결 권한(403)이 정상화되어야 합니다.

### 복구 원칙
실험 테이블을 생성해도 기존 데이터는 그대로 유지합니다. 롤백은 우선 기능 플래그를 끄고 실험 API만 비활성화합니다.
데이터 삭제(DROP)는 필요성·백업을 확인한 별도 명시적 승인 없이 실행하지 않습니다.
